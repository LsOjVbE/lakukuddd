导读：你要完成的三件事

先明确"做什么"和"为什么"，再动手

很多人对"上云"的想象是一堆互相看不懂的名词：VPC、安全组、负载均衡、CI/CD……于是止步于npm run dev。这份指南要打破这个门槛，它只做三件具体的事：

🔌第一件 · 连上

在 WorkBuddy 中通过「腾讯轻量云专家」连接器授权腾讯云账号，用一句话查询、配置、排障你的 Lighthouse 实例。

🏗️第二件 · 搭台

把一台裸机服务器改造成云平台：容器运行时 + 自建 PaaS 面板 + 反向代理 + 自动 HTTPS + 备份。

🚀第三件 · 上线

用 Vibe Coding 生成一个真实项目，通过 WorkBuddy 部署到该平台，任何人访问域名就能打开。

本指南的两个关键心法 心法一：把服务器"讲清楚"给 AI。不要只在对话里口述服务器信息，而是写一份结构化的 server_info.md 作为部署目标文件，让 AI 每次都能读同一份事实来源。
心法二：把"验收标准"写进指令。不要说"帮我部署一下"，而是给出可验证的条件（端口、健康检查、回滚方式、状态码）。AI 交付质量与指令精度强相关。
安全边界提醒 教程中的命令会真实执行在云服务器上，涉及付费资源与数据。WorkBuddy 在执行脚本前会弹出确认，请务必看清三件事：要执行什么、影响范围在哪、为什么必须执行。不确定就取消，并要求它先输出将要执行的清单与备份方案。

开箱准备：十分钟列清清单

缺一样都会在中途卡住，先核对再动手

2.1 账号与资质

  • WorkBuddy 个人版账号 —— 部分云端权益仅对个人版开放，企业版不参与。
  • 腾讯云账号并完成实名认证（个人或企业），协作者与子账号不参与部分权益活动。
  • 如需绑定域名：一个已备案（国内地域服务器）或未备案（中国香港等地域）的域名，能修改 DNS 解析记录。
关于免费用机 「腾讯轻量云专家」上线期间有配套活动：在 WorkBuddy 内召唤该专家、完成 OAuth 授权并提交至少一次有效对话后，可按活动页规则领取 0 元新购或续费入门型实例 1 个月（常见规格 2核2G4M）。活动有地域限制与每日限量，具体规则、时间与库存请以腾讯云活动页实时展示为准。

2.2 本地环境

项目说明
SSH 客户端macOS / Linux 自带终端；Windows 用 PowerShell 7 或 Windows Terminal 自带 ssh，也可用 Xshell / PuTTY
Git用于代码中转（路径 B / C 需要），本地与服务器都要能访问仓库
代码编辑器VS Code 等，便于查看 Vibe Coding 生成的项目结构
密钥文件创建实例时生成的 .pem 私钥，只下载一次，务必立即妥善保存

2.3 先用两分钟，把"安全底线"设好

在还没连上服务器之前，先把本地密钥权限设对。这是新手最常踩的第一个坑：Linux / macOS 下 .pem 权限过宽，SSH 会直接拒绝连接。

本地终端（macOS / Linux / WSL）
# 把下载的私钥放到统一目录，并收紧权限（必须是 600）
mkdir -p ~/.ssh
mv ~/Downloads/lighthouse_key.pem ~/.ssh/lighthouse_key.pem
chmod 600 ~/.ssh/lighthouse_key.pem

# 首次连接时确认指纹，正常输入 yes 即可
ssh -i ~/.ssh/lighthouse_key.pem root@你的公网IP
Windows 用户注意 Windows 上 .pem 文件若继承了 Users 组或 Everyone 的权限，SSH 同样会报 "UNPROTECTED PRIVATE KEY FILE"。在 PowerShell 7 中先重置 ACL 再使用：
PowerShell 7（管理员）
icacls .\lighthouse_key.pem /inheritance:r
icacls .\lighthouse_key.pem /grant:r "$($env:USERNAME):(R)"
ssh -i .\lighthouse_key.pem root@你的公网IP

2.4 建立"部署事实来源"：server_info.md

这是本指南最值得带走的一个习惯。把服务器的关键信息写成一个固定文件放进项目目录，AI 在每次部署任务中读同一份事实来源，避免"记错 IP""搞混环境"。

deploy-kit/server_info.mddeploy kit
# 部署目标（唯一事实来源）
CLOUD=腾讯云 Lighthouse
REGION=ap-shanghai
PUBLIC_IP=123.45.67.89
SSH_USER=deployer
SSH_KEY=~/.ssh/lighthouse_key.pem
APP_NAME=my-vibe-app
APP_PORT=3000
DOMAIN=app.example.com
私钥绝不入库 server_info.md 只写路径，不要写私钥内容；把私钥文件放进 .gitignore。任何时候都不要把私钥贴进对话、README 或公开仓库。

3.2 选型：配置怎么选才不浪费

用途推荐规格关键约束
纯静态页 / 轻量定时任务 2 核 2G 系统盘 ≥ 40G。构建镜像时内存容易吃紧，务必加 Swap
自建 PaaS 面板 + 1~3 个应用 2 核 4G（推荐起点） 面板自身及内部组件会常驻占用约 0.4 ~ 1.2G 内存
多应用、带数据库 4 核 4G 及以上 磁盘建议 ≥ 40G；数据库与对象存储分离规划
三个选型细节 ① 镜像：新手选 Ubuntu 22.04 / 24.04 LTS 或 Debian 系统镜像，生态最好、文档最多；想省事也可直接选 Docker 应用镜像，但系统版本可能偏旧。
② 登录方式：优先密钥对，比密码更安全，也免去记忆负担。
③ 磁盘：自建 PaaS 面板的安装过程需要拉取多个镜像并跑内部数据库，系统盘低于 16G 极易在中途报 "No space left on device"，建议 40G 起步。

3.3 用 WorkBuddy 配置防火墙（最容易漏的一步）

Lighthouse 的云侧防火墙（安全组）和服务器内部的系统防火墙（ufw / iptables）是两套独立规则，两层都要放行。很多人只开了云侧，结果被内部防火墙拦住，排查半天。

一句话让 AI 配好云侧规则
WorkBuddy 对话prompt
请为我的 Lighthouse 实例（实例 ID：lhins-xxxxxx）配置防火墙规则：
放行 TCP 22（仅限我的常用出口 IP）、80、443，
并告诉我当前已生效的全部规则。
注意区分云侧安全组与系统内 ufw，两层状态都汇报给我。

系统侧（SSH 登录后执行）：

服务器终端
# 只放行必要端口，其余默认拒绝
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw --force enable
sudo ufw status verbose
Docker 会绕过 ufw 容器发布的端口是由 Docker 直接写 iptables 规则开放到公网的，ufw 拦不住。所以容器端口务必绑定回环地址（127.0.0.1:3000:3000），由反向代理统一对外，或在 DOCKER-USER 链中显式限制来源。

阶段二 · 把一台服务器改造成云计算平台

目标：具备容器调度、可视化面板、反向代理与自动 HTTPS 的可用平台

"云计算平台"听起来很大，落到一台轻量服务器上其实是四层能力的叠加：容器运行时 → 管理面板 → 反向代理 → 证书与备份。下面按顺序落地。

4.1 基础加固

服务器终端 · 初始化
# 1) 更新系统
sudo apt update && sudo apt upgrade -y

# 2) 时区与时间同步（云 API 签名对时间偏差极其敏感）
sudo timedatectl set-timezone Asia/Shanghai
sudo apt install -y chrony
sudo systemctl enable --now chrony
timedatectl

# 3) 创建日常运维用户（不要长期用 root）
sudo adduser deployer
sudo usermod -aG sudo deployer
sudo rsync --archive --chown=deployer:deployer ~/.ssh /home/deployer

4.2 安装 Docker 引擎

服务器终端
# 官方一键脚本
curl -fsSL https://get.docker.com | sudo sh
sudo systemctl enable --now docker
sudo usermod -aG docker deployer

# 验证（重新登录使用户组生效）
docker --version
docker run --rm hello-world

接着配置镜像加速与日志轮转。Lighthouse 实例在腾讯云内网中，可直接使用内网镜像源，拉取速度更快：

/etc/docker/daemon.json
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json > /dev/null <<'EOF'
{
  "registry-mirrors": ["https://mirror.ccs.tencentyun.com"],
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
EOF
sudo systemctl restart docker
docker info | grep -A2 Registry
为什么一定要配日志上限 不限制日志大小的话，一个话多的容器几周就能把磁盘写满，然后整个平台的数据库、构建缓存一起崩。把 max-size 和 max-file 写进全局配置，是"零成本防灾"。

4.3 加 Swap（2G 内存机型的救命配置）

镜像构建阶段是内存峰值时刻。没有 Swap 的 2G 机型很容易触发 OOM Killer，把构建进程或面板自身杀掉。

服务器终端
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h

4.4 装一个"云控制台"：三种路线任选

这是把服务器"变成平台"的关键一步。装上面板后，后续部署不再需要敲命令，改为点点点或 git push。

方案定位特点适合谁
Coolify 开源自建 PaaS Heroku 式体验；GUI + CLI；Git 推送即部署；280+ 一键应用模板；内置 Let's Encrypt；监控与数据库支持最全。资源占用相对高 首选推荐。想要"最完整、最不容易踩坑"
Dokploy 开源自建 PaaS 单文件安装、极轻量（空闲内存约 350MB）；原生多服务器 / Docker Swarm 集群；自带 Traefik；SSL 默认需手动开启 熟悉 Docker、想要横向扩展与集群
宝塔面板 服务器运维面板 全中文、图形化；网站 / 数据库 / SSL / Python 项目一键添加；教学演示友好 教学内容展示、需要中文界面
Portainer 纯容器管理面板 只管 Docker：镜像、容器、Compose、网络、卷的可视化管理 只想管容器，不需要 PaaS 那层抽象
也可以让 AI 直接装 三种方案都可在 WorkBuddy 中用一句话驱动，例如：
WorkBuddy 对话prompt
请在服务器 123.45.67.89 上安装 Coolify（自建 PaaS 面板）。
要求：
1. 使用官方安装脚本，安装完成后报告面板访问地址与初始账号；
2. 确认 Docker 与 Traefik 组件已正常运行；
3. 把面板端口加入云侧防火墙，并说明如何在控制台看到它；
4. 全程输出每一步实际执行的命令与结果，不要省略报错。

动手安装（以 Coolify 为例，其余方案同理）：

服务器终端
# Coolify —— 默认面板端口 8000
curl -fsSL https://cdn.coollabs.io/coolify/install.sh | sudo bash

# 或者 Dokploy —— 默认面板端口 3000
# curl -fsSL https://dokploy.com/install.sh | sudo sh

# 查看面板是否已起来
sudo docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
面板端口先别急着对公网开 初次访问建议用 SSH 隧道，避免面板登录页直接暴露在公网被扫描爆破：
本地终端 · SSH 隧道
ssh -i ~/.ssh/lighthouse_key.pem -L 8000:localhost:8000 deployer@123.45.67.89
# 然后在本地浏览器打开 http://localhost:8000 完成初始化注册
初始化并在面板里绑定域名与开启 HTTPS 之后，再撤销隧道、关闭公网直连端口。

4.5 反向代理与自动 HTTPS

面向用户的入口只开放 80 / 443，由反向代理把请求转发给本机的应用端口。若使用 Coolify / Dokploy，其内置的 Traefik 会自动接管这一步，只需在面板里填域名；若使用宝塔或自行配置，则用 Nginx。

/etc/nginx/conf.d/app.conf
server {
    listen 80;
    server_name app.example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }
}
服务器终端 · 申请证书并启用 HTTPS
sudo apt install -y nginx certbot python3-certbot-nginx
sudo nginx -t && sudo systemctl reload nginx

# Let's Encrypt 自动签发并改写 Nginx 配置
sudo certbot --nginx -d app.example.com --redirect -m you@example.com --agree-tos

# 验证自动续期
sudo certbot renew --dry-run

4.6 域名解析

在域名服务商处添加一条 A 记录：主机记录填子域名（如 app），记录值填服务器公网 IP。解析生效后再申请证书，否则 Let's Encrypt 校验会失败。

没有域名也能先跑通 可以直接用 http://公网IP:端口 验证功能链路，域名与 HTTPS 属于最后的美化与安全加固环节。但正式对外服务请务必上 HTTPS，否则浏览器会标记"不安全"，且 Cookie、摄像头等能力会被限制。

4.7 平台验收清单

在下单部署项目之前，先确认平台本身是健康的：

  • Docker 服务已启用且开机自启，docker run --rm hello-world 正常
  • Swap 已挂载并写入 /etc/fstab，free -h 可见
  • 面板可通过 SSH 隧道访问，已完成初始化并设置强密码
  • 云侧防火墙与 ufw 规则一致，22 / 80 / 443 状态明确
  • 域名解析已生效：dig +short app.example.com 返回公网 IP
  • HTTPS 证书签发成功且 certbot renew --dry-run 通过

阶段三 · 用 Vibe Coding 造一个真项目

目标：从一句需求出发，产出一个可运行、可容器化、可部署的应用

5.1 什么是 Vibe Coding

Vibe Coding 指用自然语言描述意图、由 AI 完成实现与调试、你专注于"感觉对不对"的开发方式。它的关键不在于"让 AI 写代码"，而在于你能不能把验收标准讲清楚 —— 因为验收标准同时是 AI 的施工图和你的测试用例。

提示词四要素模板 一份高质量的 vibe coding 指令，通常包含以下四段：
通用提示词模板prompt
【目标】用一句话说清楚这是什么、给谁用。
【技术栈】语言/框架/版本，以及明确不要用的东西。
【验收标准】可被逐条检查的行为清单（页面能打开、接口返回什么、数据存哪里）。
【工程约束】目录结构、环境变量、必须包含 /healthz 健康检查、需要用 Dockerfile 打包。

5.2 一个完整示例

假设你要做一个"个人作品集 + 留言板"。在 WorkBuddy 里发起任务：

WorkBuddy 对话 · Vibe Coding 指令prompt
请帮我开发一个「个人作品集 + 留言板」网站。

【目标】展示我的 3 个作品，访客可留下一条留言。
【技术栈】Node.js 20 + Express + 原生 HTML/CSS/JS，数据存本地 SQLite 文件，
          不要引入 React 等前端框架，不要用外部 CDN 资源。
【验收标准】
  1. 首页展示作品列表，移动端单列、桌面端三列；
  2. 提交留言后立即出现在列表中，无需刷新整页；
  3. 留言过长（>200 字）返回 400 并给出提示；
  4. GET /healthz 返回 200 与 {"status":"ok"}。
【工程约束】
  1. 端口从环境变量 PORT 读取，默认 3000；
  2. 提供 .env.example、README.md（含启动说明）；
  3. 提供可用的 Dockerfile，使用 alpine 基础镜像，非 root 用户运行；
  4. 数据文件路径可通过环境变量配置，便于挂载持久化卷。

先给出目录结构与实现计划，我确认后再写代码。

5.3 本地跑通，再谈部署

本地终端
npm install
npm run dev          # 或 node server.js
curl http://127.0.0.1:3000/healthz
"本地正常"≠"线上正常" 最常见的三处差异：① 环境变量（本地写死，线上没有）；② 文件路径与大小写敏感（Linux 严格区分大小写）；③ 监听地址（本地 localhost，容器内必须是 0.0.0.0 才能被代理访问）。这三条务必在部署前自查。

5.4 补齐工程化产物

Dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
ENV NODE_ENV=production PORT=3000
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s \
  CMD wget -qO- http://127.0.0.1:3000/healthz || exit 1
CMD ["node", "server.js"]
docker-compose.yml
services:
  app:
    build: .
    restart: unless-stopped
    env_file: .env
    ports:
      # 关键：绑定回环地址，只让反向代理访问
      - "127.0.0.1:3000:3000"
    volumes:
      - ./data:/app/data
为什么端口要写 127.0.0.1 写成 3000:3000 等于把容器端口直接暴露到公网，绕过 ufw 与本机反向代理，安全与可观测性都变差。写成 127.0.0.1:3000:3000，流量必须经 Nginx / Traefik，才能统一做 HTTPS、限流与日志。

6.2 路径 B · Git 中转部署（推荐）

先在服务器上克隆仓库，之后每次更新只需执行一个脚本。

服务器终端 · 首次部署
sudo mkdir -p /opt/my-vibe-app
sudo chown deployer:deployer /opt/my-vibe-app
git clone git@github.com:you/my-vibe-app.git /opt/my-vibe-app
cd /opt/my-vibe-app
cp .env.example .env      # 填入线上真实配置

/opt/my-vibe-app/deploy.sh · 一键更新
#!/usr/bin/env bash
set -euo pipefail

APP_DIR=/opt/my-vibe-app
PORT=3000

cd "$APP_DIR"
git fetch --all
git reset --hard origin/main
docker compose up -d --build

# 健康检查：不通就报错退出，便于发现线上异常
for i in $(seq 1 15); do
  if curl -fsS "http://127.0.0.1:$PORT/healthz" >/dev/null; then
    echo "✅ 部署成功，服务已就绪"
    exit 0
  fi
  sleep 2
done

echo "❌ 健康检查失败，请查看 docker compose logs" >&2
exit 1
为什么要内置健康检查 部署脚本"执行完了"和"服务真的可用"是两件事。在脚本里加一段重试式健康检查，可以把"静默失败"变成"明确报错"。这条习惯能省下大量"页面白屏但日志无异常"的排查时间。

07

运维与安全：让平台活下去

上线只是开始，稳定性来自几条固定的纪律

7.1 安全基线（六条）

  • 仅密钥登录：在 /etc/ssh/sshd_config 中设 PasswordAuthentication no，重启 sshd。
  • 禁用 root 直登：日常使用 sudo 用户，PermitRootLogin no。
  • 最小端口暴露：只开 22 / 80 / 443；面板端口优先走 SSH 隧道，不长期对公网开放。
  • 及时更新：开启 unattended-upgrades，自动安装安全补丁。
  • 失败登录防护：安装 fail2ban，对暴力破解自动封禁 IP。
  • 密钥轮换：人员变动或疑似泄露时立即更换密钥对并重新分发。
服务器终端 · 安全加固片段
sudo apt install -y fail2ban unattended-upgrades
sudo systemctl enable --now fail2ban

# 关闭密码登录（确认密钥登录已可用后再执行！）
sudo sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sudo sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
sudo systemctl restart sshd

# 确认：另开一个终端还能正常密钥登录，再关掉当前会话
改 SSH 配置前，先确认还有一条能进的通道 关闭密码登录后如果密钥失效，就彻底进不去了。正确做法是：先另开一个终端验证密钥登录成功，再关闭当前会话；同时提前在腾讯云控制台确认可用的 VNC / 远程登录兜底方式。

维度做法
主机指标Lighthouse 控制台自带监控（CPU / 内存 / 带宽 / 磁盘）；也可让轻量云专家查询监控数据并输出趋势
容器状态docker ps / 面板内置监控；设置 restart: unless-stopped 保证异常退出自动拉起

🌿基础设施即代码

7.4 成本控制

  • 到期提醒：在日历上标注实例到期日。部分套餐到期后可能转为按量计费，不留神会持续产生费用。
  • 免费实例≠长期环境：免费期结束若不再续费，实例释放后数据会一并消失。重要数据务必走 Git 或对象存储。
  • 按需升配而非一步到位：轻量服务器支持升级配置，起步选 2核2G / 2核4G，撑不住再升。
  • 流量与带宽：轻量套餐自带月流量包，静态大文件建议放对象存储 + CDN，避免打满流量。

排障速查表

先按现象定位层级，再逐层排除
通用排查顺序 服务是否在跑 → 监听地址对不对 → 系统防火墙 → 云侧安全组 → 反向代理 → 域名解析 → 证书。逐层验证，不要跳步，也不要一上来就改配置。
现象可能原因排查方向
SSH 连不上 密钥权限过宽 / 端口未放行 / IP 不在白名单 本地 chmod 600 私钥；确认云侧 22 端口规则；检查是否被 fail2ban 封禁
服务已启动，外网打不开 云侧安全组未放行，或服务只监听 127.0.0.1 两边都查：控制台防火墙规则 + ss -lntp | grep 端口 看监听地址
云侧开了还是不通 系统内 ufw / iptables 拦截 sudo ufw status verbose、sudo iptables -L -n 双重确认
容器端口绕过了防火墙 Docker 直接写 iptables，ufw 管不住 端口绑定 127.0.0.1；或在 DOCKER-USER 链中加限制规则
依赖安装失败 / 超时 源不可达或架构不匹配 换国内镜像源：pip 用清华源、npm 用国内源、Docker 用内网加速；确认 uname -m 架构
构建中途磁盘写满 系统盘不足 / 镜像与日志堆积 df -h、docker system prune -a；面板与多应用建议 40G 起步
进程被无故杀掉 内存不足触发 OOM Killer dmesg | grep -i oom 确认；加 Swap、限制构建并发、升级配置
云 API 签名失败 服务器时间偏差超限 timedatectl 检查，chrony 同步时间
面板登录页被频繁扫描 面板端口直接暴露公网 改用 SSH 隧道访问；绑定域名 + HTTPS；开启登录失败锁定
HTTPS 证书签发失败 域名未解析到本机 / 80 端口不通 先 dig +short 域名 确认解析，再确认 80 可被公网访问
授权返回 403 scope 不足 / token 过期 / 回调不匹配 重新完成连接器授权，核对权限范围
部署"成功"但页面白屏 环境变量缺失 / 前端资源 404 / 监听地址错误 看容器日志；检查 .env 与构建产物路径；确认监听 0.0.0.0
把排障也交给 AI
WorkBuddy 对话prompt

每一步都给出实际命令与实际输出，最后给出根因与最小修复方案：

进阶玩法

平台搭好之后，能力可以持续向上叠加

① 静态产物的"零运维"通道

如果你交付的只是单文件 HTML，未必需要上服务器。WorkBuddy 的轻量发布可以把本地 HTML 一键上传为在线链接（workbuddy.link 域名），配合 CSV 作为数据源还能做成可用的轻应用。

选型建议：纯展示、无需后端 → 轻量发布；需要数据库 / 常驻服务 / 自定义域名 → 走本文的 Lighthouse 平台。

② 把 WorkBuddy 自身托管上云

Lighthouse 提供应用模板，可一键部署自托管 WorkBuddy 服务，由系统自动完成域名、SSL 与扩缩容配置。适合希望团队共享、7×24 常驻执行定时任务的场景。

注意：2核4G 起步可支撑小团队（约 5–10 人）并发使用；并发需求高时再升配。

③ CI/CD 流水线

把部署脚本接到 GitHub Actions：推送 tag 触发构建 → 构建镜像推送到镜像仓库 → SSH 到服务器拉取并重启。原文中的 deploy.sh 即是流水线的最后一环。

④ 多环境与灰度

用两份 Compose 文件区分 staging 与 production，各自独立的域名与环境变量。先在 staging 验证，再切换生产，把"翻车半径"压到最小。

⑤ 横向扩展

Dokploy 原生基于 Docker Swarm 支持多服务器部署，加入 Worker 节点即可获得调度、负载均衡与故障转移；Coolify 则以中央面板独立管理多台服务器，控制力更强但需自行配置路由。

⑥ AI 驱动的日常运维

让轻量云专家定期做巡检：查询监控趋势、核对防火墙规则、检查证书到期时间、汇总异常日志。把重复的运维动作变成一句定时指令。
